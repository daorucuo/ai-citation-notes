同一句“必须”，写在三个地方，只有一个真算数

2026-10-28

它读到了，只是那份东西的效力，和你在对话框里随口说的半句话一样。

2026-10-26，技术论坛 V2EX 上有人发了条帖子，标题是一句气话：

“Claude 是傻逼吗，我写的强制性规范，它能直接不看的吗”

我读到这条，去翻了一份官方文档。文档里承认了这件事，写得很直白，直白到有点不像官方该说的话。

这篇里的事实，一半是我读到的官方文档，一半是我从论文摘要里读到的，没有一件是我自己跑出来的。出处都写在句子里，能查的去查。

文档里那句话，写得比谁都直白

Anthropic 给 Claude Code 写的使用文档里，有一节叫「故障排查」。里面有个小标题，叫「Claude 没有遵守我的 CLAUDE.md」。原文是英文：

“CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself.”

翻成人话：你写的那份规范，是作为一条用户消息送进去的，排在系统提示后面，不属于系统提示。同一份文档里还有一句更短的：

“Claude treats them as context, not enforced configuration.”

它把这份文件当上下文，不当配置。

这句话解释了很多人的困惑。你以为自己在写规章，它拿到手的是一段聊天记录。这段记录里有你的问题、你贴的代码、它自己的上一句回答。你的规范混在里面，谁更靠前，由它现场判断。

文档还给了两个数字边界。单个文件建议 200 行以内，超过会在启动时给警告。硬上限 4 MiB，超过这个数的文件直接跳过，一个字都不加载。管记忆的那个索引文件，每次对话只读前 200 行或前 25KB，哪个先到算哪个。

所以“写了三十条必须，它一条没照做”这件事，不是它叛逆。它读到了，只是那份东西的效力，和你在对话框里随口说的半句话是一样的。

有人把它改成命令，管用了一阵

再往下翻同一份文档，它自己给了另一条路：

“To block an action regardless of what Claude decides, use a PreToolUse hook instead.”

要挡住一个动作，不管模型怎么决定，就用 PreToolUse hook。这类钩子是程序，在每次用它手上工具之前跑。返回一个“拦住”，那个动作就真的不执行。模型没有推翻它的手段。

这就是第二个地方：写进拦截里。同一个动作，比如 git push --force。写成一句“禁止强推”，它可能照做。写成一段判断命令的脚本，它推不出去。

文档里还有一句，把两件事分得很清楚：CLAUDE.md 影响行为，但不是强制层。

到这里，多数讨论就收尾了——规范没用，上拦截。我也差点写成这样。

然后我读到两件绕过去的事

第三件事实来自 2026-10-27 的 arXiv。编号 2610.32045，标题大意是“做科研的 Agent 还保得住模型安全吗”。作者拿 5 个 agent 框架、50 条有害的化学请求、4 个 GPT 变体做对照，发现一件反直觉的事。装上框架之后，连最普通的直接提问，模型给出有害回答的比例都变高了。而那些对裸模型基本无效的对抗性提问，装上框架之后突然变得很有效。

框架本来是加防护的。加完，底座模型原本守住的那条线，没了。

第四件来自同一批的另一篇，编号 2604.27819，叫 MCPHunt，是修订版。它测的是另一种情况。每一个动作都拿到了许可，但数据从 A 服务器流到 B 服务器，凭据跟着一起过去了。3615 条轨迹、5 个模型、147 个任务，这种越界传播的比例在 11.5% 到 41.3% 之间。它还跟走哪条路径强相关：同一个模型，换个机制，从 0.0% 到 74.4%。集中出现的地方是浏览器经手的那一段。

这两条合起来说的是同一件事：拦截管的是这一次的动作，管不了两次都合规、合起来出事。

还有第三个数，我觉得比前两个更值得记住。编号 2610.32285 的那篇，把 agent 框架的可靠性单独拿出来评分。4 个框架、9 个模型、95 个任务，一共 3420 次运行。结论里有一句：31.1% 的运行，任务做成了，但至少违反了一条框架判据。

做成了，和做对了，是两件事。

第三个地方，它连试都试不了

文档里还有第三段话，这一段很少有人提：

“Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer.”

设置层的规则由客户端执行，不管模型怎么决定。

对应的是权限配置和沙箱开关：permissions.deny、sandbox.enabled。写在这里的东西，模型读不到，也不用读。那个工具、那个目录、那个网络出口，它压根够不着。它不是被劝住的，它够不着那条路。

这个区别看着小，落到工程上差很远。编号 2610.32851 的那篇讲企业知识库，里面有个数字我一直记着。241 个代码仓库、18 个服务，走完一条完整的业务流，会牵出一千多条名字几乎一样、含义完全不同的规则。

用向量检索去找，它会把另一个服务里那条几乎一样的规则返回给你。相似度很高，而且不报任何错。

作者的做法是把归属信息放到每条工件的身上：这条规则属于哪个服务、哪个模块、哪个版本。查询先落在工件上，再在里面搜。这样那条不该出现的规则，是不存在，不是排在后面。

不存在和排在后面，是两个世界的事。

同一批里还有一篇讲重试的，编号 2610.31916。它把“重试”这一步单独拿出来测。336 条执行历史，两种主流编排框架做对照，14 种调度、3 种供应商契约、4 套应用策略交叉。

结果是这样的。直接拿缓存重试，42 个用例过 30 个。重试之前先重新校验一次，过 36 个。用稳定的幂等键重试，过 31 个。而保留完整账本、事后逐笔对账的那一套，42 个全过。

重试这个动作，平时没人给它定规矩。它恰恰是最容易出事的地方。

一把能带走的尺子

我把上面这些压成三句话，是我自己在用的，不是行业标准。

第一问：这条规矩删掉，会出错吗？

不会，就删掉。留着只会占掉那份文件本来就不多的额度。

第二问：会出错，那它能不能写成一句“如果……就拦住”？

能，就写成拦截。写得出来，就别用文字求它。

第三问：写不成拦截的呢？

那它大概不是一条规矩，是一条边界。边界不该写在文件里，该写进谁能碰、碰哪一层、碰完谁来对账。

第三问最难，因为它要求你先承认：有些事你没法在它动手那一刻拦住，只能提前把路修窄，或者事后一笔一笔查。

这条判断在哪儿不成立

有一种情况我到现在也没解决：该不该做。规矩能管怎么做，拦截能管不许这么动。但“这个需求本身该不该接”，三处都写不进去。这类判断还是得人看，而且得在它动手之前看。

所以三个地方不是三级升级，是三种不同的活。文件里放偏好和背景，拦截里放硬性禁止，结构里放那些一旦发生就没法挽回的事。

混着用的结果，是文件越写越长，长到 200 行以上。然后它开始选择性忽略。而你恰好把最在意的那条写在了最后。

那份 V2EX 帖子里，最扎人的其实不是标题。是它证明了一件事：一个人认认真真写了几十条“必须”，最后得到的反馈是“它好像没看见”。

它看见了。这才是让人难受的地方。
